# Система сверки БУ-ПУ (НПФ)

Автоматизированная система сверки бухгалтерского учёта (**БУ**) и персонифицированного учёта (**ПУ**) для негосударственного пенсионного фонда.

Система читает входные файлы (Excel и JSON) из двух директорий, нормализует данные, суммирует по датам, сравнивает суммы по каждому из 14 показателей и формирует итоговый Excel-отчёт с листами «Свод» и «Детализация».

## Запуск

### Шаг 1 — Разместите входные файлы

Поместите файлы ПУ в папку `data/ПУ/`, файлы БУ — в `data/БУ/`.

Если папки не существуют, программа создаст их сама при первом запуске и сообщит об этом.

### Шаг 2 — Запустите программу

```bash
python -m npf_recon
```

Результат — файл `output/Сверка_БУ_ПУ.xlsx`.

#### Параметры командной строки

```bash
python -m npf_recon --help
python -m npf_recon --generate-sample          # создать демо-данные и сразу свериться
python -m npf_recon --data-dir /path/to/data   # переопределить базовую папку
python -m npf_recon --period "Март 2026" --eps 0.01 --output out.xlsx
python -m npf_recon -v                          # подробный лог (DEBUG)
```

### Генерация тестовых данных

```bash
python scripts/generate_sample_data.py
```

Создаёт синтетические файлы в `data/ПУ/` и `data/БУ/` за 9 дат февраля, с
разнообразными форматами дат (`DD.MM.YYYY`, `DD.MM.YY`, ISO, datetime) и сумм
(обычный/неразрывный/узкий пробел, запятая-разделитель, скобки и завершающий
минус для отрицательных), несколькими операциями в один день и строками,
которые должны игнорироваться. Заложены **три** расхождения:
1. «Страховой резерв» на 17.02.2026: БУ − ПУ = +15 000,00 (по итогу).
2. «Пенсионные взносы ФЛ» на 28.02.2026: БУ − ПУ = +5 000,00 (по итогу).
3. «Целевые взносы ЮЛ»: месячные итоги БУ и ПУ **равны**, но есть встречные
   дневные отклонения — 10.02 (+7 000) и 24.02 (−7 000). Демонстрирует
   обнаружение расхождений на уровне дней даже при совпадении итогов.

## Настройка путей

По умолчанию данные читаются из `data/ПУ` и `data/БУ` (относительно корня репозитория).

### Переменные окружения

| Переменная | Описание |
|---|---|
| `NPF_DATA_DIR` | Переопределяет базовую директорию данных; подпапки ПУ и БУ берутся из настроек YAML |
| `NPF_PU_DIR`   | Прямой абсолютный путь к папке ПУ |
| `NPF_BU_DIR`   | Прямой абсолютный путь к папке БУ |

Пример для продуктивной среды Windows:

```bat
set NPF_PU_DIR=C:\Сверка БУ-ПУ\Приложение_1\ПУ
set NPF_BU_DIR=AI-1С:\Сверка БУ-ПУ\Приложение_1\БУ
python -m npf_recon
```

## Реестр файлов → показатели

### Папка ПУ

| Подстрока в имени файла | Показатель | Формат | Колонка даты | Колонка суммы |
|---|---|---|---|---|
| `Выплата` | маппинг по ВидВыплат → 3 показателя | Excel с заголовком | «Дата операции» | «Сумма» |
| `Пенсионные взносы ФЛ` | Пенсионные взносы ФЛ | Excel | A (0) | H (7) |
| `Пенсионные взносы ЮЛ` | Пенсионные взносы ЮЛ | Excel | A (0) | H (7) |
| `Целевые взносы ФЛ` | Целевые взносы ФЛ | Excel | A (0) | H (7) |
| `Целевые взносы ЮЛ` | Целевые взносы ЮЛ | Excel | A (0) | C (2) |
| `Страховой резерв` | Страховой резерв | Excel | A (0) | I (8) |

Маппинг `ВидВыплат`:
- «Негосударственная пенсия» → **Выплата пенсии**
- «Выкупная сумма (Расторжение)» → **Выплата выкупных сумм**
- «Выкупная сумма (Наследникам)» → **Выплата наследуемых сумм**

### Папка БУ

| Подстрока в имени файла | Показатель | Формат | Примечание |
|---|---|---|---|
| `397.03 Страховой резерв` | Страховой резерв | Excel | A=дата, I=сумма |
| `НПО` | 4 показателя взносов | JSON | маппинг по `components[].name` |

Маппинг компонентов JSON:
- «Пенсионные взносы ФЛ по договорам НПО» → **Пенсионные взносы ФЛ**
- «Пенсионные взносы ЮЛ по договорам НПО» → **Пенсионные взносы ЮЛ**
- «Целевые взносы ФЛ» → **Целевые взносы ФЛ**
- «Целевые взносы ЮЛ» → **Целевые взносы ЮЛ**

## Гибкость и устойчивость

- **Колонки** в `mappings.py` можно задавать как индексом (0-based: `7`), так и
  буквой Excel (`"H"`) — парсер понимает оба варианта.
- **Заголовки** файла «Выплата» распознаются без учёта регистра и лишних
  пробелов; для каждого логического столбца можно указать список синонимов.
- **Нормализация чисел** понимает обычный/неразрывный/узкий пробел, запятую и
  точку как десятичный разделитель, бухгалтерские скобки `(1 234,56)`,
  завершающий минус `1 234,56-`, Unicode-минус `−`, валютные обозначения
  `₽ / руб. / RUB` и прочерк `–` как пустое значение.
- **Расхождения** фиксируются и по итогу за период, и по каждому дню — день
  попадает в отчёт, даже если месячные итоги БУ и ПУ совпали.
- **Парсеры** переиспользуются (кэш реестра) — без повторного создания объектов
  на каждый файл.

## Переход на API (портируемость)

Вся бизнес-логика (агрегация, сверка, отчёт) работает исключительно с нормализованными объектами `Record` — она **не знает** ничего о формате источника.

Чтобы перейти от чтения файлов к получению данных через API, нужно:

1. Создать класс `ApiSource`, реализующий абстракцию `Source` из `src/npf_recon/sources/base.py`:

```python
class ApiSource(Source):
    def __init__(self, api_url: str, token: str, pu_period: str, bu_period: str):
        ...

    def scan(self) -> list[RawDocument]:
        # Обращается к API, получает список документов/отчётов,
        # возвращает RawDocument с path=VirtualPath (или BytesIO-обёрткой)
        ...
```

2. При необходимости добавить парсеры для новых форматов ответа API (наследники `Parser`).

3. В `pipeline.py` заменить `FileSystemSource(...)` на `ApiSource(...)`.

Слои `aggregate.py`, `reconcile.py`, `report.py` и все тесты — **остаются без изменений**.

---

## Архитектура (слои)

```
Source → RawDocument → Parser → Record → Aggregate → Reconcile → Report
  ↑                      ↑
 (заменяется           (добавляется новый
  при переходе         парсер для нового
  на API)              формата ответа API)
```
